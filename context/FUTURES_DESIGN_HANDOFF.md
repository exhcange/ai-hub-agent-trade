## Published facts versus unresolved contracts

- Ordinary order `orderUnit` is documented as 1 coin / 2 contracts / 3 value, default 2. Exact conversion, legal combinations, rounding, and limits still need agreement; the basic enum is already available.
- Position mode requires `contractName` and `positionModel` (1 net / 2 two-way); margin mode requires `contractName` and `marginModel` (1 cross / 2 isolated). Margin adjustment requires `positionId` and `amount`; leverage requires `contractName` and `nowLevel`. Preconditions, effective scope, and readback remain open.
- TP/SL `profitLossOrder` documents an array of at most five entries, orderUnit 2 only, positive integer quantity, triggerType 1 stop-loss / 2 take-profit, and type 1 limit / 2 market. The ordinary condition endpoint instead describes triggerType as 3UP/4DOWN. They must not share enums by assumption.
- `futures-version: 101` is listed on order creation, condition creation, TP/SL, trigger cancellation, and current trigger list. This does not establish that every signed endpoint requires it.
- Futures candles document `1h`, unlike the current spot `60min`. Candle examples use ten-digit `idx` values while the field description says milliseconds.
- `/ticker` names its parameter as human-readable "Contract name"; `/index` includes an unexplained limit; GET `/order` is labeled Request Body and marks orderId required while also listing clientOrderId.
- `/cancel_all` documents no body fields. Its execution-time scope cannot be inferred from a preview snapshot.
- Ordinary order examples include IDs beyond JavaScript safe integer range. Converting an already-rounded Number to a string does not recover the original ID. Lossless parsing must be designed alongside decimal handling.
- Published TP/SL success JSON and trigger-cancel response JSON contain syntax errors. They are not executable fixtures. Obtain corrected samples rather than silently repair and treat them as authoritative.
- The public document mixes raw results and code/msg/data examples and has an incomplete ordinary-business transaction type description. General signing documentation and safe failure examples still require verification.
